# Автоматическая калибровка RAG

Рабочий документ. Разбор того, как калибровка порога устроена сейчас, и пять способов сделать её
автоматической. Способ 1 реализован, остальные — предложения.

---

## 1. Как было устроено до этого документа

Порог отсечения в `Use RAG` целиком держался на «пробах», которые должен написать человек.

1. **Настройки** — `FreeAIr/Options2/Rag/RagJson.cs`: `Sensitivity` (0.2 по умолчанию) и узел
   `Calibration` с двумя списками: `Relevant` (запрос + ожидаемый файл) и `Irrelevant` (запросы,
   на которые в решении ответа нет). `Relevant` по умолчанию пуст; пустой `Irrelevant` заменяется
   встроенным набором из пяти строк про грибной суп и погоду
   (`RagCalibrationProbes.DefaultIrrelevant`, `Search/Find/RagCalibration.cs`).
2. **Замер** — `RagCalibrator.RunAsync`: одним батчем векторизует все пробы; для каждой безответной
   берёт top-1 по индексу, `NoiseCeiling = max` этих скоров; для каждой размеченной ищет ожидаемый
   файл в top-50, `RelevantFloor = min` найденных, ненайденные считаются промахами.
3. **Порог** — `EmbeddingCalibration.ComputeThreshold`: `noise + sensitivity * (1 − noise)`, сверху
   ограничен `RelevantFloor − 0.25·(floor − noise)`.
4. **Когда** — один раз в конце построения индекса
   (`BuildNaturalLanguageOutlinesJsonFileToolViewModel.CalibrateAsync`) и вручную из окна
   `RagCalibrationViewModel` («Probe → Mark as answer / Mark as hopeless → Recalculate → Save»).
   Числа лежат в метаданных индекса, запросы — в настройках, поэтому переживают перестройку.
5. **Применение** — `RagShortlist.RunAsync`: `minScore` отсекает хвост ранжированного списка.

Идея правильная: порог как доля пути от измеренного шума до идеала — единственное, что переносится
между моделями. Слабые места — в статистике и в том, что весь полезный вход должен написать
человек:

- `NoiseCeiling` — **максимум по пяти наблюдениям**: один выброс определяет порог для всего решения.
- Встроенные безответные запросы намеренно далеки от кода. Шум, померенный на «рецепте грибного
  супа», сильно ниже шума на правдоподобном «как тут настроен ретрай http-клиента» — порог
  получается заниженным, и фильтр де-факто не фильтрует. Это признано в комментарии к
  `RagCalibrationProbes` как известная слабость.
- `RelevantFloor` — **минимум**, то есть одна плохая метка обнуляет защиту.
- Интерполяция к `1.0` предполагает, что косинус реального запроса может дойти до единицы. У многих
  моделей потолок реального попадания ~0.6–0.7 — значит `Sensitivity = 0.2` всё-таки означает на
  разных моделях слегка разное, хоть и несравнимо меньше, чем голый косинус.
- `Relevant` пуст у 100% пользователей, которые не открывали окно калибровки.

## 2. Способ 1: пер-запросная нормализация — РЕАЛИЗОВАН

### Идея

`EmbeddingIndex.Search` — линейный скан, он **уже считает скор каждой записи индекса** и потом
выбрасывает всё, кроме top-K. То есть для каждого запроса у нас бесплатно есть полное распределение
похожести по всему корпусу: тысячи чисел, из которых релевантны единицы. Это идеальная выборка
шума — причём шума, померенного *на этом самом запросе*, а не на суррогате.

Порог:

```
threshold = median + k · sigma,   sigma = (median − P25) / 0.6745,   k = 2 + 5·Sensitivity
```

Почему именно так:

- **медиана, а не среднее** — устойчива к тому, что несколько верхних записей действительно
  релевантны;
- **разброс по нижней половине** (`median − P25`), а не MAD и не по верхней половине: верхняя
  половина — это как раз ответы, и разброс, померенный через них, рос бы каждый раз, когда запрос
  срабатывает; порог поднимался бы ровно тогда, когда поиск работает. Нижняя половина не
  загрязняется релевантными попаданиями в принципе;
- **деление на 0.6745** переводит межквартильную полуширину в единицы обычной сигмы, так что `k`
  читается как «сколько сигм над фоном»;
- список уже отсортирован по убыванию — медиана и квартиль стоят три обращения к массиву, второй
  проход и вторая сортировка не нужны.

Что это даёт:

- ноль обращений к модели, ноль новых настроек, работает на свежесобранном некалиброванном индексе;
- снимает и разницу масштабов между моделями, и «хабность» запроса: короткий общий запрос близок ко
  всему корпусу, распределение сдвигается целиком, порог едет вместе с ним. Глобальный
  `NoiseCeiling` этого не умеет в принципе — он одно число на весь индекс;
- «ничего не нашлось» становится честным ответом: если top-1 не отрывается от медианы, отдавать
  нечего.

### Что сделано

| Файл | Изменение |
|---|---|
| `Search/Embedding/ScoreDistribution.cs` | новый тип: `Count`, `Best`, `Median`, `LowerQuartile`, производные `RobustSigma` и `BestDeviations`, `ComputeThreshold(sensitivity)`, `Measure(отсортированный скан)` |
| `Search/Embedding/EmbeddingIndex.cs` | перегрузка `Search(..., out ScoreDistribution?, ...)`; распределение снимается **до** обрезки головы, старая трёхаргументная сигнатура сохранена и делегирует в новую |
| `Search/Find/RagShortlist.cs` | `minScore = max(калибровка, распределение)`; `RagShortlistResult.Distribution` для окна калибровки |
| `FreeAIr/Options2/Rag/RagJson.cs` | обновлён `[Description]`: `Sensitivity` больше не бездействует на некалиброванном индексе |

Ключевые решения:

- **`MinimumSampleSize = 256`.** Квартили десятка чисел — не квартили. На индексе меньше 256 записей
  пер-запросный порог не выдаётся вовсе (возвращается 0 = «без порога»), а не выдаётся выдуманный.
  Побочный эффект: все существующие тесты на индексах из 2–20 узлов продолжают проверять ровно то,
  что проверяли.
- **`sigma == 0` → порога нет.** Вырожденный индекс (много одинаковых векторов) не должен приводить
  к отсечению всего.
- **Два порога перемножаются как `max`, а не заменяют друг друга.** Калибровка знает, как высоко
  забирается бессмыслица на этом корпусе; распределение знает, насколько этот конкретный запрос
  близок ко всему подряд. Каждый видит тот шум, которого не видит другой, поэтому файл обязан
  пройти оба.
- **`Sensitivity` осталась одна на оба порога**, просто читается в разных единицах: как доля пути до
  идеала в `EmbeddingCalibration`, как число сигм в `ScoreDistribution`. Новой ручки не появилось.
- В `ProbeAsync` (окно калибровки) порог по-прежнему только сообщается, а не применяется — окно
  существует ровно для того, чтобы смотреть на строки, которые он отрезал.

### Тесты

`Search.Tests/ScoreDistributionFacts.cs` (7 фактов) — квантили снимаются со всего скана, а не с
головы; пустой индекс не даёт распределения; слишком маленькая выборка и распределение без разброса
не дают порога; порог — это счёт сигм над медианой, ручка зажимается, а не экстраполируется; разброс
берётся только из нижней половины (модель с одним ярким попаданием и модель с сотней получают один и
тот же порог); одна настройка означает одно и то же на моделях разного масштаба.

`Search.Tests/RagShortlistFacts.cs` (+4 факта) — запрос, оторвавшийся от фона, проходит на индексе,
который никогда не калибровали; запрос, на который корпус не отвечает, отдаёт пустой шортлист;
файл обязан пройти оба порога (проверено в обе стороны: побеждает то калибровка, то распределение);
проба показывает строки, отрезанные пер-запросным порогом.

`Search.Tests/TestIndex.cs` — построитель индекса вынесен из `RagShortlistFacts` в общий хелпер,
добавлены `OfScore` (вектор с заданным косинусом к `(1,0)` — тест пишет нужный ранжир, а не
геометрию) и `Background` (корпус из N узлов с равномерно размазанными скорами).

Итог: `run-tests.bat` — 124 пройдено, 6 пропущено (интеграционные, без сервера), 0 упавших;
`MSBuild -t:Build -c Release` — 0 ошибок.

## 3. Способ 2: банк правдоподобных вопросов вместо пяти нелепых

Заменить `DefaultIrrelevant` на встроенный список ~100–150 коротких вопросов, **правдоподобных для
любого кода**: «где настраивается пул соединений», «как устроена миграция схемы», «где
обрабатывается отмена задачи», «how is oauth configured», плюс русские дубли. Для конкретного
решения ответа нет почти ни на один, а те немногие, на которые ответ есть, гасятся устойчивой
статистикой:

```
NoiseCeiling = P90 распределения top-1-скоров по банку   (вместо max по пяти)
```

Цена — один батч из ~150 коротких строк в конце сборки индекса, которая и так занимает десятки
минут. Самое дешёвое изменение с самым большим эффектом: шум начинает меряться на тексте той же
формы и того же домена, что и реальные запросы, и `Sensitivity` наконец начинает значить то, что про
неё написано.

Усиление: прогнать весь банк, **исключить** вопросы, у которых top-1 заметно оторвался от остальных
(вероятно, ответ действительно есть), и померить P90 по остатку.

Затрагивает: `RagCalibrationProbes.DefaultIrrelevant`, `RagCalibrator.RunAsync` (max → P90),
`EmbeddingCalibration` (новых полей не нужно).

## 4. Способ 3: автоматические размеченные пробы из самого индекса

`RelevantFloor` можно получить, не спрашивая пользователя и **не потратив ни одного вызова
эмбеддера** — все нужные векторы уже лежат в индексе.

Взять N ≈ 100 случайных записей и использовать **их собственный вектор как вектор запроса**,
исключив саму запись; ожидаемый файл — `entry.RelativePath`. У файла почти всегда есть другие узлы
(класс и его члены — про одно и то же), и скор лучшего *другого* узла того же файла есть честное
наблюдение «сколько стоит настоящее попадание на этой модели и этом корпусе». Отсюда:

```
RelevantFloor = P10 этого распределения   (вместо min по 0–3 ручным пробам)
```

Оговорка: outline-к-outline'у систематически выше, чем вопрос-к-outline'у — тексты одной формы,
то есть это оценка сверху. Лечится якорной поправкой: если у пользователя есть хоть 3–5 настоящих
ручных проб, посчитать по ним медиану отношения `реальный скор / авто-скор` и умножить авто-оценку
на неё. Так ручные пробы из обязательного входа превращаются в необязательное уточнение — что и
есть цель.

Бесплатный побочный результат — **отчёт о качестве индекса**: доля авто-проб, у которых свой файл
попал в top-50, это recall@50, измеренный без единого запроса к серверу. Низкий recall означает, что
модель не понимает этот код и никакой порог не поможет. Сейчас это видно только через
`RelevantMissCount` по ручным пробам, которых обычно ноль.

## 5. Способ 4: пробы, сгенерированные чат-моделью

Самый точный и единственный с ценой в токенах, зато снимает оговорку способа 3 — вопросы получаются
настоящими вопросами.

В конце сборки индекса, одним-двумя chat-запросами к уже настроенному агенту:

- **Положительные**: выбрать 20–30 файлов (стратифицированно по проектам, предпочитая файлы с
  содержательным outline'ом), отдать модели их outline-тексты и попросить по одному вопросу на файл,
  на который отвечает именно этот файл. → `Relevant`-пробы с готовой разметкой.
- **Отрицательные**: отдать outline'ы солюшена и проектов верхнего уровня и попросить 20 вопросов,
  правдоподобных для проекта такого рода, но **на которые здесь ответа нет** — ровно то, что в
  комментарии к `RagCalibrationProbes` описано как «только автор решения такое напишет». Модель,
  видевшая оглавление всего решения, напишет это не хуже автора.

Дальше обычный `RunAsync`, но с устойчивыми статистиками (P90/P10) вместо max/min. Имея размеченный
набор в 40–50 проб, можно подбирать **не порог, а саму `Sensitivity`**: перебрать по сетке
0.05…0.5 и взять ту, что максимизирует F-меру с перекосом в полноту (β ≈ 2 — лишний файл стоит
одного запроса к LLM, потерянный потерян навсегда, это прямо сказано в шапке `RagShortlist`). Тогда
у пользователя не остаётся ни одной ручки, которую нужно крутить.

Куда встроить: рядом с `CalibrateAsync`, за галкой в настройках. Сгенерированные пробы писать в тот
же узел `RagCalibration`, но с пометкой происхождения (`Generated = true`), чтобы окно калибровки
показывало их отдельно от ручных и не затирало ручные при перегенерации.

## 6. Способ 5: пассивная калибровка по реальному использованию

Писать в `.freeair\` небольшой журнал: на каждый реальный RAG-поиск — запрос, top-скоры,
характеристики распределения и то, какой из предложенных файлов пользователь в итоге открыл.
Открытый файл — положительная метка, бесплатная и настоящая. Через несколько десятков поисков
пересчитывать калибровку по накопленному.

Побочно даёт детектор дрейфа: если распределение top-1 поехало относительно записанного при сборке,
индекс устарел относительно кода и его пора пересобрать. После реализации способа 1 половина нужных
чисел уже считается на каждом поиске — журналировать `ScoreDistribution` практически ничего не стоит.

## 7. Порядок работ

| | Изменение | Цена | Эффект | Статус |
|---|---|---|---|---|
| 1 | Пер-запросная нормализация | 0 запросов | Порог работает даже на некалиброванном индексе | **сделано** |
| 2 | P90/P10 вместо max/min в `RunAsync` | ~20 строк | Убирает зависимость от одного выброса | предложение |
| 3 | Банк правдоподобных вопросов | 1 батч ~150 строк на сборку | Шум меряется на тексте нужной формы | предложение |
| 4 | Авто-`RelevantFloor` из индекса + recall@50 | 0 запросов | `Relevant` перестаёт быть обязательным | предложение |
| 5 | Генерация проб LLM + автоподбор `Sensitivity` | 1–2 chat-запроса на сборку | Ручек не остаётся вовсе | предложение |
| 6 | Журнал использования | фоново | Калибровка уточняется сама | предложение |

Шаги 2–4 не требуют ни одного нового обращения к модели сверх того, что уже происходит, и совместимы
с текущим форматом метаданных: `CalibrationJsonObject` придётся расширить только полями
распределения, старые индексы продолжат читаться.

Мерить регресс есть чем: `Search.Tests` содержит `RagCalibrationFacts` и
`RagCalibrationIntegrationFacts`, а интеграционные тесты умеют ходить в настоящий эмбеддинг-сервер
через `FREEAIR_TEST_EMBEDDING_ENDPOINT`. Естественные метрики — recall@15 и число файлов, прошедших
порог, на наборе из способа 3.
